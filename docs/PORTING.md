# Cross-platform port

## Current architecture

The playable target is intentionally a 32-bit Windows DLL. It is loaded into a patched
`terranx.exe`, reads original game state through fixed virtual addresses, and calls original code
that has not yet been decompiled. Wine provides the first macOS and Linux runtime without changing
game behavior.

The DLL must preserve these contracts:

- PE32/i386 output and four-byte pointers.
- The original executable image base of `0x00400000`.
- Win32 cdecl and thiscall calling conventions.
- Reverse-engineered class and structure layouts.
- The fixed import order generated by the checked-in `ImportAdder.exe`.
- Original CRT ownership for allocations and `FILE` objects that cross the executable boundary.

The CMake build and patcher fail early when these contracts are not met.

## Native target boundary

A Mach-O or ELF build cannot use the original executable's address space. Native work should only
move into a platform-neutral target after a subsystem owns all of its state and no longer calls
fixed addresses from `temp.cpp`.

The intended progression is:

1. Keep the Wine build as the behavioral reference.
2. Inventory each original data and function binding by subsystem.
3. Finish and regression-test the corresponding reverse-engineered implementation.
4. Replace fixed globals with explicitly owned state while preserving serialized layouts.
5. Move independent code into a platform-neutral core library.
6. Add a standalone main loop after startup, input, rendering, and save/load no longer call the
   original executable.
7. Add SDL-based native platform services for macOS, Linux, and Windows.

Differential tests should run equivalent operations in the original Wine process and the native
implementation with identical inputs and random seeds. This is especially important for map
generation and AI, where small random-number or layout changes alter game behavior.

## Known reverse-engineering priorities

- `Path::find` and `Path::move` are incomplete.
- `parse_string`, `filefind_init`, and `base_psych` remain draft implementations.
- `temp.h` lists original executable functions that still need native replacements.
- Fixed-address globals across the game modules need an owned game-state model.
- GDI, User32, WinMM, profile, and file-mapping services need native platform implementations.
- Startup, the main loop, rendering presentation, input, and save/load orchestration must be
  independent before a standalone executable is viable.

Portability wrappers alone do not address these dependencies. Source changes should either finish
reverse engineering, establish verified ownership/layout boundaries, or implement a native service
after its original behavior is understood.
